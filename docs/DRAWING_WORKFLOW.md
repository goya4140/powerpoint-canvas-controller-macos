# 论文插图制作流程

## 目标

把用户的研究方法转化为可验证、可编辑、可升级的 PowerPoint 插图。流程中的源事实不是某张渲染图片，而是已经和用户确认过的 Level 1 语义图。

三个 Level 是递进关系：

1. **Level 1：语义骨架。** 用框、线、箭头、文字和基本几何确认技术含义。
2. **Level 2：模块视觉化。** 在不改变结构的前提下，用图标或轻量卡通元素替换选定模块。
3. **Level 3：插画叙事化。** 在统一画风中组织角色与场景，但继续保留 Level 1 作为结构对照层。

## 阶段总览

| 阶段 | 关键问题 | 输入 | 输出 | 用户确认 |
|---|---|---|---|---|
| 0. 目标定义 | 这张图让读者理解什么？ | Method、草图、伪代码、已有图 | Figure Brief | 技术范围与目标版面 |
| 1. 语义建模 | 有哪些节点、边、分组与贡献？ | Figure Brief | Level 1 JSON 规格 | 技术关系是否正确 |
| 2. 结构候选 | 哪种阅读模型最合适？ | 已验证语义图 | 2–3 张线框候选 | 选择布局并修正边界 |
| 3. Level 1 定稿 | 论文尺寸下是否清晰？ | 选中候选 | 可编辑 PPTX + 预览 | 确认结构冻结 |
| 4. Level 2 升级 | 哪些模块值得图标化？ | Level 1 + 素材库 | 图标化 PPTX | 资产、配色与语义一致 |
| 5. Level 3 升级 | 插画是否增强而非遮蔽信息？ | Level 2 + 画风设定 | 插画主导版本 | 角色、场景与构图 |
| 6. QA 与交付 | 导出后是否仍准确、清晰、可编辑？ | 最终 PPTX | PPTX/PDF/SVG/PNG | 最终验收 |

## 阶段 0：Figure Brief

只收集会改变图形的信息：

- 一句话核心信息和目标读者；
- 输入、输出、主要模块与方法贡献；
- 数据流、控制流、反馈、更新、分支和层级；
- 系统边界、泳道、共享资源与外部组件；
- 单栏、双栏、整页或演示尺寸；
- 必须保留的符号、术语和现有 PPTX 对象。

不确定的关系要显式标记。文本中的先后叙述不自动等于因果关系，也不能因为画面“需要一条线”而虚构技术连接。

## 阶段 1：建立 Level 1 语义图

按照 [`references/level-1-grammar.md`](../references/level-1-grammar.md) 把内容编码为节点、边和分组：

- 节点使用稳定 ID，如 `skill-selector`；
- 边区分 `data`、`control`、`feedback`、`update`、`optional`；
- 分组只表达真实的阶段、模态、系统或所有权边界；
- 未来需要图标化的节点声明语义化 `asset_slot`，如 `robot`、`database`、`network`；
- 不在 Level 1 中绑定“可爱蓝色机器人”之类的具体画风。

在绘制之前运行：

```bash
node scripts/validate_level1_spec.mjs --spec <figure.json>
```

必须消除重复 ID、未知引用、不合法主路径环路、过长标签和布局元数据错误。

## 阶段 2：生成结构候选

一次提供 2–3 个**结构不同**的候选。例如：

- Pipeline：突出输入到输出的主变换；
- Swimlane：突出 Agent/Environment、Training/Inference 或不同模态；
- Hub-spoke：突出规划器、记忆库或调度器的中心作用；
- Hierarchy：突出管理者—工作者、任务分解或多尺度关系；
- Overview + inset：总览确认后再展开一个贡献模块。

颜色变化、圆角变化或间距变化不算新的结构候选。每个候选都要先渲染检查，排除因空间位置暗示错误执行顺序的方案。

## 阶段 3：Double Check 与 Level 1 定稿

向用户确认五件事：

1. 阅读方向和箭头方向；
2. 是否有漏掉、错误合并或错误拆分的模块；
3. 论文贡献应当位于哪里、强调到什么程度；
4. 系统边界、共享资源和外部组件是否正确；
5. 选中的布局及目标论文宽度。

用户确认前不写入 `selected_layout`，也不把某个候选当作定稿。确认后冻结以下结构合同：

- 节点 ID、标签与坐标；
- 边 ID、方向与类型；
- 分组成员和边界；
- 主阅读方向；
- 贡献模块的相对强调。

随后在目标论文尺寸下检查文字、间距、连线、灰度辨识度和对象可编辑性。

## 阶段 4：Level 2 模块替换

Level 2 不是重画，而是基于 `asset_slot` 的受控替换：

1. 从组件库检索与节点语义匹配的图标或轻卡通元素；
2. 继承节点的颜色语义和连接锚点；
3. 保持原节点 ID、坐标、边、分组和标签；
4. 只在必要时微调模块内部排版；
5. 对新增资产记录来源、许可、风格标签和可编辑性。

适合图标化的对象包括 LLM/Agent、用户、数据库、网络、工具、环境和评价模块。重复出现的资产应放在单独的 `COMPONENTS` 页或组件库中，而不是散落为不可追踪的图片。

## 阶段 5：Level 3 插画升级

Level 3 需要先建立视觉系统，再进行组合：

- 确定角色设定、线条粗细、色板、透视和阴影规则；
- 先制作可复用角色、场景和状态组件；
- 用角色动作和场景关系承载技术叙事；
- 保留 Level 1 对照页，逐项核对节点与边；
- 任何因插画尺寸导致的结构改动都必须再次征得用户确认。

强视觉不能牺牲论文缩放后的标签可读性，也不能让装饰性箭头与真实技术边混淆。

## 阶段 6：QA 与交付

### 技术检查

- 每个节点和边都能追溯到用户提供的方法；
- 主路径、反馈与更新的箭头语义明确；
- 定稿与用户确认的候选一致；
- 没有用视觉位置暗示不存在的因果关系。

### 视觉检查

- 无溢出、遮挡、意外换行或连线穿过标签；
- 字号在目标论文宽度下可读；
- 对齐、间距、圆角、线宽和箭头一致；
- 颜色语义稳定，灰度下仍可区分。

### PowerPoint 检查

- 主要模块均为独立可编辑对象；
- 移动模块时连接线仍附着；
- 对象名称来自稳定语义 ID；
- 资产替换后仍能追溯到唯一 `asset_slot`；
- 最终图没有被整体扁平化为位图。

最终至少交付可编辑 PPTX 和渲染预览；按需求补充 PDF、SVG 或高分辨率 PNG。

## 返工规则

- **技术关系变化：** 回到阶段 1，更新语义图并重新生成受影响候选。
- **布局不合适：** 回到阶段 2，不必重做已确认的技术内容。
- **图标不合适：** 只替换对应 `asset_slot`，不改 Level 1。
- **插画破坏结构：** 以 Level 1 对照页为准恢复结构，再调整视觉构图。

这种分层返工可以让技术修改、版式修改和画风修改彼此解耦。
